UNITED DELHI — VPS BACKEND DEPLOYMENT

OVERVIEW
The GitHub workflow .github/workflows/deploy-vps.yml deploys only when server/** changes on main.
It waits 20 seconds, compares the event's server tree with current main, and skips stale snapshots.
GitHub concurrency permits one active workflow and only the newest pending workflow. A burst of source commits therefore gets one deployment of the final server snapshot, not one backend build for every intermediate commit.

The VPS deployment is disabled until the repository variable VPS_DEPLOY_ENABLED is exactly "true".
The deployment uses an isolated release directory, runs Node.js 22 checks/tests on GitHub and the VPS, atomically switches /opt/united-delhi/current, restarts systemd, checks Neon connectivity, and rolls back to the previous release if the new one fails.

REQUIREMENTS
- Ubuntu 22.04/24.04 or a supported Debian release.
- VPS public IP/hostname and SSH access as root for initial setup.
- A dedicated Ed25519 SSH key for GitHub Actions.
- A Neon DATABASE_URL and Transport Stack API key.
- A public HTTPS API hostname will be needed before switching app/ and web/ off the current Render URL.

INITIAL VPS SETUP
1. From a local clone after pulling main, copy server/deploy files to the VPS:
   scp -r server/deploy/* root@YOUR_VPS_HOST:/tmp/united-delhi-deploy/
   (Create /tmp/united-delhi-deploy on the VPS first if scp reports that the directory is missing.)
2. Run interactively:
   ssh -t root@YOUR_VPS_HOST "bash /tmp/united-delhi-deploy/bootstrap-vps.sh"
   Paste the SSH PUBLIC key when asked. Never paste the private key into the VPS setup prompt.
3. Edit /etc/united-delhi/server.env as root. Fill DATABASE_URL and TRANSPORT_STACK_API_KEY. Keep the file mode 0640. Do not commit these values.
4. The bootstrap script enables systemd but does not start the API until a release is deployed.

GENERATE A DEDICATED WINDOWS SSH KEY
Run in PowerShell:
   ssh-keygen -t ed25519 -f "$env:USERPROFILE\.ssh\united-delhi-vps-deploy" -C "united-delhi-vps-deploy"
Press Enter twice when asked for a passphrase, so the unattended GitHub runner can use the key. Use this key only for deployment.
The public key is:
   $env:USERPROFILE\.ssh\united-delhi-vps-deploy.pub
The private key is the file without ".pub". Never share the private key in chat.

GITHUB REPOSITORY CONFIGURATION
Repository Settings -> Secrets and variables -> Actions -> Secrets:
- VPS_HOST: VPS IP/hostname
- VPS_USER: uddeploy
- VPS_SSH_PRIVATE_KEY: entire content of the private key (without .pub)
- VPS_KNOWN_HOSTS: verified SSH host-key line(s) for the VPS
Optional secret:
- VPS_SSH_PORT: SSH port, normally 22; when using a non-default port, VPS_KNOWN_HOSTS must use the [host]:port form.

Verify the VPS host-key fingerprint from the VPS provider console before trusting the known-hosts entry. Do not disable StrictHostKeyChecking.

Repository Settings -> Secrets and variables -> Actions -> Variables:
- VPS_DEPLOY_ENABLED = true

The workflow cannot deploy until the VPS is reachable by SSH, the public key is installed, secrets are saved, and /opt/united-delhi/releases is writable by uddeploy.

DATABASE AND SERVICE
The VPS connects to Neon using DATABASE_URL. This setup does not migrate, erase or create a new database. Do not run server/sql/001_reset_and_schema.sql manually; the app manages compatible runtime schema migrations.
The systemd unit runs as an unprivileged united-delhi user. uddeploy can restart only the united-delhi service through passwordless sudo; it cannot read the root-owned service environment file.

NETWORK AND CUTOVER
Keep port 10000 private using the VPS firewall; expose SSH and, once configured, ports 80/443 for a reverse proxy. The API app itself listens on port 10000.
Before moving the public app to the VPS, configure a domain with HTTPS (for example, with Caddy) and test:
- https://YOUR_API_HOST/health
- https://YOUR_API_HOST/api/status (database should be OK)
- https://YOUR_API_HOST/api/realtime/vehicles

Only after those checks pass should app/src/config.ts, app/eas.json, web/vite.config.ts, web/vercel.json and the CSP API origin be changed to the new HTTPS hostname. Until then both clients remain pointed at the current Render fallback.

RENDER FALLBACK
server/render.yaml now declares autoDeploy: false so blueprint-managed Render deployments do not duplicate VPS deployments. If the existing Render service is configured directly in the Render dashboard rather than synchronized from this blueprint, turn its Auto-Deploy setting off after confirming the VPS is healthy. Leave the currently running Render service available as a fallback until public API cutover succeeds.
