EXECUTIVE SUMMARY — CONFIRMED FINDINGS

1. HIGH — LIVE GTFS ROUTE IDs DO NOT MATCH THE IMPORTED STATIC ROUTE DATA
Neon read-only query (last 24 hours of vehicle_positions):
- 997 distinct non-empty live route IDs.
- 194 IDs matched a row in public.routes.
- 803 IDs had no matching static route row (80.5% unmatched).
- The realtime feed is returning live vehicles; Render logs repeatedly show successful decoded feeds. Therefore this is not simply a total realtime outage.
- Current static_feed_meta identifies the static source as ethanc8-delhi-gtfs-bus, imported 27 October 2026. Live vehicle positions come from Delhi OTD's authorised GTFS-Realtime feed.
Impact: when route_id is not found in routes, server/src/index.js cannot enrich that vehicle with short_name/long_name and falls back to routeId. That is why internal values such as 1324/3476 appear instead of public route numbers.
Required fix:
- Obtain/import the static GTFS published for the SAME OTD feed/network/version used by the realtime producer, or build a verified route-ID crosswalk using matching trip/route identifiers. Do not assume route IDs from unrelated feeds are interchangeable.
- Validate a join against current live route IDs before any production replacement. Require high coverage and inspect unmatched samples before approval.
- Keep route IDs as internal identifiers; display route_short_name first, then route_long_name, and only show an internal ID as an explicitly labelled fallback.
- Do not truncate or replace production static tables until the new archive is validated and a rollback snapshot is confirmed.

2. HIGH — ALL 2,403 STATIC ROUTES HAVE NULL short_name
Read-only query against public.routes:
- total routes: 2,403
- short_name missing/blank: 2,403 (100%)
- long_name missing/blank: 0
The current importer parses routes.txt route_short_name and includes short_name in its INSERT, so the database result alone does not prove whether the source archive had blank route_short_name values or an earlier import populated the database differently. The original ZIP used for the 27 October import was not available in this audit to settle that question.
Required fix:
- Inspect the exact imported routes.txt and compare it with the matching current OTD static feed.
- If the source has public route labels in route_long_name, use that field as the long-name value and preserve route_desc separately if needed.
- Add an import validation report for blank route_short_name counts and route label quality; reject or explicitly warn on a feed where all public short names are blank.
- Add tests for public route labels including 772, 801, 801STL and AIR-5.

3. HIGH — GTFS route_long_name / route_desc FIELD MAPPING IS REVERSED
server/scripts/import-dtc-static.mjs currently assigns:
  long_name: clean(row.route_desc || row.route_long_name, 500)
GTFS route_desc is a description; route_long_name is the route's long name. Preferring route_desc can store a descriptive string instead of the actual public route name whenever both are populated.
Required fix: prefer route_long_name for routes.long_name; retain route_desc in a separate column if the product needs it. Test both fields populated and route_desc-only feeds.

4. HIGH — CURRENT ROUTE LABEL FALLBACK IS WORKING AS WRITTEN, BUT CANNOT REPAIR MISSING DATA
server/src/route-display.js checks short_name, then long_name, then a fallback. That behavior is sensible. The failure is upstream: 803 live route IDs do not join to the static table, and all 2,403 short_name values are blank. Changing only the display helper will not fix this.
Required fix: correct feed compatibility and imported route fields first, then keep the helper fallback and regression tests.

5. HIGH — CURRENT BUS COLOUR SYSTEM DOES NOT IMPLEMENT THE PROPOSED FOUR-COLOUR OPERATOR MATRIX
Render logs repeatedly report 0 exact per-vehicle colours supplied by the Delhi OTD realtime feed. Neon currently has 5,576 fleet registry rows and 0 vehicle_livery_verifications rows.
Current server/src/vehicle-color.js classifies only a limited set of known registration prefixes (some EV and DL1P* DTC registrations). It does not classify DIMTS/private-cluster buses from agency/operator data. The service() wrapper receives an agency argument but does not pass it into classifyFleetTypeFromRegistration; the classification therefore ignores agency_id.
Current Android/web category defaults are fuel/body-category based:
- CNG Non-AC -> orange
- CNG AC -> blue
- EV DEVI AC -> light green
The UI has no red DTC CNG AC category and does not distinguish DTC vs DIMTS operator. The default category resolver also returns null for EV AC (12 mtr); the test explicitly expects that null.
Required fix:
- Model operator, fuel/propulsion, AC status, and marker colour as separate attributes. Do not overload serviceType or busType with paint colour.
- Add verified operator classification using GTFS agency_id (DTC/DIMTS) where reliable, plus vehicle registration/fleet records. Add a separate fuel/AC classification from trusted fleet metadata.
- If the user's proposed mapping is accepted after validation, implement it as a category-display mapping:
  DTC + CNG + Non-AC -> green
  DTC + CNG + AC -> red
  DIMTS + CNG + Non-AC -> orange
  DIMTS + CNG-or-electric + AC -> blue
- Treat that mapping as provisional until verified against authoritative DTC/DIMTS fleet records. A blue bus cannot by itself prove whether it is CNG or electric. Do not claim these are exact physical paint colours unless there is per-vehicle evidence.
- Keep exact upstream or reviewed per-vehicle livery as a separate higher-priority physical-colour source. OTD logs show the feed currently provides zero such colours.
- Update Android and web implementations and all corresponding tests together.

6. MEDIUM/HIGH — FLEET REGISTRY CAN PERMANENTLY PRESERVE AN INITIAL UNKNOWN CLASSIFICATION
server/src/index.js seeds vehicle_fleet_registry rows using the currently available registration/label data and inserts with ON CONFLICT(vehicle_id) DO NOTHING. If a vehicle is first seen without useful registration data, it can be stored as Unknown; later improved metadata for the same vehicle ID will not refresh that row automatically because the existing registry entry is skipped.
Required fix: distinguish manually reviewed rows from automatically inferred rows; refresh auto rows when stronger metadata arrives; never overwrite manual verification; record classification source and confidence.

7. MEDIUM — STATIC FEED IS STALE RELATIVE TO THE PREVIOUSLY REVIEWED NEWER ARCHIVE
Current Neon metadata says source ethanc8-delhi-gtfs-bus, imported 27 October 2026, with 2,403 routes, 10,559 stops and 99,286 route-stop links. The previous project audit recorded a supplied newer DTC archive with 2,554 routes and 6,812 stops that had not been imported. That archive was not attached to this audit, so its contents and compatibility could not be revalidated here.
Required fix: compare the exact newer archive to the current feed and realtime route IDs, then use the protected import workflow only after review. Do not blindly import merely because its route count is higher.

8. MEDIUM — METRO DATA IS TOPOLOGY-ONLY, NOT CURRENT TIMETABLE DATA
Prior audit records state the Metro calendar ended 31 December 2025. Current Neon contains 18 Metro route groups and 262 stations. The old calendar must not be represented as current operating schedules or timetable coverage.
Required fix: import a current authoritative Metro schedule/calendar before showing timetable-based claims. Until then label Metro results as topology-based estimates and avoid claiming live schedule accuracy.

ADDITIONAL SOURCE / PRODUCT FINDINGS

A. Route data quality and import validation
- Current static route table has no short_name values at all. Import code parses route_short_name and persists it, so compare the exact ZIP contents with the database and determine whether the archive itself has blank values.
- Current importer prefers route_desc over route_long_name. Fix this mapping and add explicit tests.
- Route-ID cross-source matching must be tested before import. A feed that has many routes/stops but a poor join with realtime IDs is not suitable for live display.
- Add metrics for route-ID join coverage, missing short names, missing route long names, duplicate public labels, unmatched live vehicle routes, and route labels that look like internal IDs.
- Avoid silently converting all missing labels to an ID without exposing a diagnostic count.

B. Bus colours and fleet data
- Current code is conservative about physical livery: standard GTFS-Realtime does not provide a standard physical bus-paint field, and current OTD logs show no exact colours.
- The app and web should show an operator/fleet-category marker using validated metadata, not pretend that a guessed category is verified physical paint.
- Add explicit operator, fuelType, airConditioned, serviceType, vehicleClass, markerColor, markerColorSource, and (only when verified) physicalLiveryColor fields or equivalent typed structures.
- Add DIMTS registration/vehicle examples to tests; ensure unknown/private-cluster records do not get incorrectly classified as DTC.
- Add a test for EV AC (12 mtr), which currently resolves to no category default.

C. Legal and documentation staleness
- The Terms of Service link to THIRD_PARTY_NOTICES.txt has been corrected.
- Terms of Service effective/last-updated date is 4 October 2026; Privacy Policy is 16 October 2026. Review and align dates when the legal text is next revised.

- Legal copy is an engineering review, not legal advice.

D. Operational / UX hardening

- Add alerting for repeated malformed realtime payloads, missing required protobuf header, feed returning zero valid vehicles, and route metadata coverage falling below an agreed threshold.

- Validate route planner estimates against real-world travel times and label all estimates clearly; previous project notes state planner durations are estimates.
